# Деплой и откат на VPS

Скрипты: `scripts/deploy.sh`, `scripts/rollback.sh` (общие функции — `scripts/deploy_common.sh`).
Запускаются **вручную на VPS**, CI/CD нет.

> Путь к проекту на VPS ниже — `/opt/PythonProject`, как в `MIGRATIONS.md` и `BACKUP_RESTORE.md`.
> Если у вас он другой, замените его в первой команде `cd`.

> ⚠️ Скрипты проверены локально (Docker Desktop, отдельный compose-проект): деплой, падение при старте,
> медленный старт, миграция, отказ отката из-за схемы, downgrade + откат, очистка образов. **На реальном
> VPS они ещё не запускались** — первый деплой делайте, когда есть время проследить за ним глазами.

---

## Как устроены образы

| Тег | Что это |
|-----|---------|
| `bot:<sha>` | образ конкретного коммита (`git rev-parse --short HEAD`), собирается один раз при деплое |
| `bot:current` | указатель на образ, который работает сейчас |

`compose.yaml` поднимает `bot:current`, поэтому `docker compose up -d`, `restart` и перезагрузка VPS
запускают **задеплоенный** образ, а не то, что лежит в git. Старые `bot:<sha>` не удаляются
автоматически — на них и делается откат.

Журнал всех деплоев и откатов: `.deploy_history` в корне проекта (не в git). Столбцы: дата, действие,
тег, предыдущий тег, ревизия Alembic, результат (`ok` / `failed`).

---

## Порядок: сначала схема БД, потом код

Это правило, а не рекомендация:

1. **Бэкап** (`deploy.sh` делает его сам, см. ниже).
2. **Изменения схемы.** Штатно — миграцией Alembic в том же коммите, что и код. Её применяет сам бот
   при старте нового образа (`run_migrations()`), **до** того как начинает обрабатывать сообщения, в одной
   транзакции. Отдельно запускать ничего не нужно.
   Если нужна **разовая ручная операция** со схемой или данными (разметка `alembic stamp`, исправление
   данных перед миграцией, в исключительном случае ручной `ALTER TABLE`, как когда-то с
   `group_message_id`), — она выполняется **до** `deploy.sh`, никогда не после. Новый код не должен
   стартовать на схеме, которая ему не подходит. Помните правило из `MIGRATIONS.md`: схему руками штатно не
   меняем, любое такое изменение потом должно быть отражено в миграциях, иначе Alembic и база разойдутся.
3. **Код** — `deploy.sh`.

Как писать и проверять миграции — `MIGRATIONS.md` §3.

## Первичная настройка (один раз)

```bash
cd /opt/PythonProject
git pull
chmod +x scripts/deploy.sh scripts/rollback.sh scripts/backup_db.sh
```

Дальше обычный деплой. Первый запуск соберёт `bot:<sha>` и `bot:current`; предыдущего образа для
отката ещё нет. Образ, который собирался до этих скриптов (имя по умолчанию `<каталог проекта>-bot`,
например `pythonproject-bot`), можно удалить, когда убедитесь, что всё работает: `docker image ls` →
`docker rmi <имя>`.

## Обычный деплой

```bash
cd /opt/PythonProject
./scripts/deploy.sh
```

Что делает скрипт по шагам:

1. Отказывается работать, если в рабочем дереве есть незакоммиченные изменения отслеживаемых файлов.
2. `git pull --ff-only`.
3. Собирает `bot:<sha>` (`docker compose build --pull bot`). Старый бот в это время продолжает работать.
4. Сравнивает ревизию Alembic в новом образе с ревизией в БД. Если отличается — печатает
   `ВНИМАНИЕ: при старте применится миграция схемы: X -> Y`.
5. **Бэкап БД** через `scripts/backup_db.sh` — пока старый бот ещё работает, простоя не добавляет. Файл:
   `backups/backup-YYYY-MM-DD-HHMMSS-predeploy-<sha>.sql.gz` (уникальное имя — не затирает ни ежедневный
   бэкап, ни бэкап предыдущего деплоя). Если бэкап не удался, деплой прерывается и старый бот продолжает
   работать.
6. Переставляет `bot:current` на новый образ и пересоздаёт контейнер `bot` (`db` не перезапускается).
7. Проверяет, что бот поднялся: до 12 попыток с паузой 5 с (~1 мин). Успех — в логе появилась строка
   `Bot is ready` (её пишет `run.py` после миграций и успешного `getMe`, то есть токен и связь с Telegram
   рабочие). Если контейнер упал или уже перезапустился — провал сразу, не дожидаясь всех попыток.
   Настраивается переменными `DEPLOY_CHECK_ATTEMPTS` и `DEPLOY_CHECK_INTERVAL`.
8. Пишет строку в `.deploy_history`.

Успешный вывод заканчивается так:

```
[...] Бот поднялся (попытка 2/12): в логе есть 'Bot is ready'
[...] Деплой 1a2b3c4 завершён (предыдущий образ: 9f8e7d6)
[...] Откат при необходимости: ./scripts/rollback.sh 9f8e7d6
```

**Запишите предыдущий тег** из последней строки — это ваша точка отката. Он же есть в `.deploy_history`.

Если в выводе `ДЕПЛОЙ ... НЕ ПОДНЯЛСЯ` — скрипт покажет хвост логов и готовую команду отката, код выхода 1.
Переходите к разделу «Откат».

### Флаги

```bash
./scripts/deploy.sh --no-backup   # не делать бэкап перед деплоем
./scripts/deploy.sh --yes         # не задавать вопросов (см. «Повторный деплой после отката»)
```

`--no-backup` **игнорируется**, если деплой применит миграцию: перед изменением схемы бэкап обязателен.

## Откат

> **Откат образа НЕ откатывает схему БД.** Это два разных действия. `rollback.sh` переключает только
> работающий образ. Если между целевым образом и текущим была миграция, схему нужно вернуть отдельно
> (шаг 2 ниже) — иначе старый код не стартует: `alembic upgrade head` падает с
> `Can't locate revision identified by '...'`, контейнер перезапускается по кругу (проверено).

### 1. Выбрать образ

```bash
cd /opt/PythonProject
./scripts/rollback.sh --list
```

Покажет образы `bot:<sha>` от новых к старым (`*` — работает сейчас) и последние записи
`.deploy_history`. Нужен последний тег с результатом `ok` до проблемного деплоя.

### 2. Откатить

```bash
./scripts/rollback.sh 9f8e7d6
```

Принимает короткий или полный sha. Пересборки нет, переключение занимает секунды + проверка запуска
(те же попытки, что при деплое).

Перед переключением скрипт сравнивает ревизию Alembic в целевом образе с ревизией в БД:

- **Совпадает** → переключает, проверяет, что бот поднялся. Готово, переходите к шагу 3.
- **Не совпадает** → печатает `ОТКАТ ОСТАНОВЛЕН` и ничего не меняет. Значит, проблемный деплой применил
  миграцию. Выполните по порядку (скрипт печатает эти же команды с нужной ревизией):

  ```bash
  docker compose stop bot
  BACKUP_LABEL=pre-downgrade ./scripts/backup_db.sh
  docker compose run --rm bot alembic downgrade <ревизия целевого образа>
  ./scripts/rollback.sh 9f8e7d6
  ```

  `alembic downgrade` запускается **текущим** образом (`bot:current`): только в нём есть файл
  миграции с функцией `downgrade()`, в старом образе её нет. **Downgrade может удалить данные** —
  например, колонку вместе со всем, что в неё успели записать после деплоя. Перед ним загляните в
  `downgrade()` этой миграции (`migrations/versions/`), а бэкап выше не пропускайте.

  Если downgrade невозможен или опасен — альтернатива не откатывать образ, а быстро выпустить
  исправление вперёд (новый коммит + `deploy.sh`).

`--ignore-schema-check` отключает эту проверку. Используйте, только если точно знаете, что старый код
с текущей схемой стартует (например, миграцию уже вернули вручную другим способом).

### 3. ОБЯЗАТЕЛЬНО: `git revert` проблемного коммита — ДО следующего `deploy.sh`

`rollback.sh` **намеренно не трогает git**: репозиторий на VPS остаётся на HEAD, то есть на проблемном
коммите. Если после отката просто запустить `deploy.sh` ещё раз, `git pull --ff-only` ничего не
изменит (в origin тот же коммит), и скрипт пересоберёт и выкатит **тот же сломанный коммит** заново.

Поэтому после отката:

```bash
# на своей машине (или прямо на VPS, если там настроен push)
git revert <sha проблемного коммита>
git push
```

и только потом на VPS:

```bash
cd /opt/PythonProject
./scripts/deploy.sh
```

Если проблемный деплой содержал миграцию и вы её откатили `alembic downgrade`, revert уберёт и файл
миграции — схема и код снова согласованы. Исправленную версию выпускайте новым коммитом с новой миграцией
(правило `MIGRATIONS.md`: применённую миграцию не редактируем).

### Повторный деплой после отката

Страховка на случай, если шаг 3 забыт: если собираемый коммит — тот самый, **с которого** последний раз
откатывались (по `.deploy_history`), `deploy.sh` печатает предупреждение и спрашивает подтверждение.
Без терминала (или без `--yes`) — отказ. Отвечайте `y`, только если коммит действительно хотите
выкатить снова (например, проблема была во внешнем сервисе, а не в коде).

## Очистка старых образов (вручную, когда сами решите)

Образ занимает около 300 МБ, но базовые слои (Python, зависимости) у соседних образов общие, так что
реально место съедают в основном изменившиеся слои. Автоматически ничего не удаляется.

```bash
cd /opt/PythonProject
./scripts/deploy.sh --prune-images 5    # оставить 5 последних + текущий
docker image prune                      # убрать слои без тегов
```

Скрипт покажет список на удаление и спросит подтверждение (`--yes` — без вопроса). Образ, который
работает сейчас (`bot:current`), не удаляется никогда, даже при `--prune-images 0`. На удалённый образ
откатиться нельзя — только пересборкой (`git checkout <sha>` + сборка вручную).

## Не делайте

- **`docker compose up --build`** и **`docker compose build bot`** для деплоя: сборка из HEAD перезапишет
  `bot:current` в обход тегов, бэкапа, проверки схемы и `.deploy_history`. Для деплоя — только `deploy.sh`.
- **`docker compose down -v`** — удалит volume с базой (см. `BACKUP_RESTORE.md`).
- Не запускайте `deploy.sh` сразу после отката без `git revert` (см. «Откат», шаг 3).
- Не меняйте файлы проекта прямо на VPS — `deploy.sh` откажется работать с грязным деревом.
